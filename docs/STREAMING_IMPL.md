# Реализация потоковой загрузки: фаза 1

Документ фиксирует только то, что реально сделано в ветке `stream2` по
плану STREAMING.md: проверяемый cook и mount, C range API, семантику гостевого
чтения и очередь/prefetch фазы 2. GPU-публикация, интеграция с кадром и
таблица клеток не реализованы и здесь не заявлены.

## Формат `stream_index.bin` (schema 1)

Только little-endian, без JSON и zlib. Все смещения таблиц кратны 8, кроме
пула путей, который дополняется нулями до 8 байт.

### Заголовок, 80 байт

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | magic `SRNX` |
| 4 | 2 | версия схемы (`1`) |
| 6 | 2 | размер заголовка (`80`) |
| 8 | 2 | размер записи архива (`56`) |
| 10 | 2 | размер записи ресурса (`104`) |
| 12 | 2 | размер записи клетки (`64`) |
| 14 | 2 | флаги: бит 0 — little-endian, остальные 0 |
| 16 | 4 | число архивов |
| 20 | 4 | число ресурсов |
| 24 | 4 | число клеток (`0` в фазе 1) |
| 28 | 4 | резерв, 0 |
| 32 | 8 | generation |
| 40 | 8 | смещение таблицы архивов (`80`) |
| 48 | 8 | смещение таблицы ресурсов |
| 56 | 8 | смещение пула путей |
| 64 | 8 | смещение таблицы клеток |
| 72 | 8 | полный размер файла, включая CRC |
| конец−4 | 4 | CRC-32 всех предыдущих байтов |

`generation` — не время сборки. Это первые 8 байт SHA-256 от канонического
дайджеста: имена/размеры/SHA-256 архивов в порядке приоритета и все поля
ресурсов (id, путь, архив, физический диапазон, stored size, флаги, оба
хеша). Повторный cook тех же входов даёт тот же generation и те же байты.

### Запись архива, 56 байт

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | смещение имени в пуле |
| 4 | 4 | длина имени |
| 8 | 8 | размер файла |
| 16 | 32 | SHA-256 файла архива |
| 48 | 4 | приоритет: индекс в списке `manifest["archives"]`, 0 — старший |
| 52 | 4 | число строк ресурсов, указывающих на архив |

### Запись ресурса, 104 байта, отсортированы по нормализованному пути

| Смещение | Размер | Поле |
|---:|---:|---|
| 0 | 4 | id (равен индексу строки) |
| 4 | 4 | смещение пути в пуле |
| 8 | 4 | длина пути |
| 12 | 4 | индекс архива |
| 16 | 8 | физическое смещение payload (после префикса записи) |
| 24 | 4 | длина payload — диапазон, доступный устройству |
| 28 | 4 | stored size из каталога архива |
| 32 | 4 | stored offset из каталога архива |
| 36 | 4 | флаги: бит 0 — сжатый архив, бит 1 — embedded name |
| 40 | 32 | SHA-256 записанного payload |
| 72 | 32 | SHA-256 исходного победителя до cook |

Путь нормализован: нижний регистр, разделитель `\`, без ведущих/хвостовых
разделителей и без компонентов `.`/`..`. Строго возрастающий порядок путей
проверяется и при записи, и при загрузке — по нему идёт бинарный поиск.

Все физические смещения получены переоткрытием архива `BsaArchive`, поиском
`find()` и чтением реального префикса (`embedded name`, затем 4-байтный
размер для сжатых). Ни одно смещение не выведено из имени части, порядка
каталога или оценки конвертера.

### Таблица клеток

В schema 1 `cell_count = 0`. Формат записи зафиксирован на будущее (64 байта):
`key[24] | neighbour_count u32 | flags u32 | 32 байта id классов`. Пустая
таблица не требует смены схемы.

## Проверка после записи

`write_index()`:

1. перечитывает файл через device-facing парсер и требует побайтового
   round-trip;
2. переоткрывает каждый архив через `BsaArchive` и сверяет размер и SHA-256
   с манифестом;
3. для каждой строки сверяет `entry.offset`/`entry.size`, пересчитывает
   физический диапазон, проверяет `offset + length` в границах файла и
   `< 2^32`;
4. читает payload через `read_file()` и сверяет длину и SHA-256;
5. сравнивает набор путей архива (`iter_files()`) с набором строк индекса —
   пропущенный или лишний файл прерывает cook.

Несовпадение размера или SHA-256 архива/файла — отказ, а не запись индекса.

## C range API

```c
BsaStatus bsa_read_range(const BsaArchive *archive, const BsaEntry *entry,
                         uint32_t rel, void *dst, uint32_t n,
                         uint32_t *out_len, char *reason, size_t reason_cap);
```

- после `entry_prefix()` проверяется `rel <= payload_len` и
  `n <= payload_len - rel`; арифметика в `uint64_t`, переполнение невозможно;
- физический адрес складывается в 64 битах, `read_exact()` пишет сразу в
  `dst`; malloc на всю запись отсутствует;
- `rel == payload_len` при `n == 0` — валидное пустое чтение в конце;
- ошибка: `*out_len = 0`, именованная причина, байты не публикуются;
- сжатая запись: `BSA_ERR_UNSUPPORTED` (cooked-архивы несжатые);
- `bsa_read()`/`bsa_read_prefix()` не изменены и по-прежнему понимают
  сжатые записи.

`stream_mount_read()` дополнительно сверяет `entry.offset`/`stored_size` с
индексом: изменившийся каталог даёт `STREAM_ERR_FORMAT`, архив неверного
размера — отказ при первом открытии.

## Метрики и negative cache

`StreamMetrics`: `requests`, `bytes_requested`, `bytes_returned`, `misses`,
`errors`, `negative_hits`, `physical_reads`, `archive_opens`.

Negative cache — 64 слота, ключ FNV-1a нормализованного пути; попадание
действует только при совпадении поколения. `stream_index_negative_reset()`
очищает кэш; новый индекс — новое поколение и новый объект.

## Фаза 2: очередь, бюджет и готовность в RAM

Реализовано в `source/asset_stream.{h,c}`; GPU-публикации, клеточной таблицы
и интеграции с TESV по-прежнему нет.

| Механизм | Реализация |
|---|---|
| Дескрипторы | 256 слотов, handle = 24-битная эпоха + 8-битный слот; устаревший handle отвергается |
| Ключ/дедуп | `(generation, source, id, lod)`; повторный запрос возвращает тот же handle, повышает приоритет и может расширить окно |
| Приоритет | строго `demand > P0 > P1 > P2`; при равном приоритете — ближайший дедлайн, затем архив и физическое смещение |
| Дедлайны | мс по монотонным часам mount; истёкший невостребованный запрос переходит в `CANCELLED`, начатый квант не рвётся |
| Состояния | `queued → reading → verified → ready`; ошибка/отмена освобождает буфер и оставляет терминальный дескриптор до `release`/`cancel` |
| Исполнитель | один активный `bsa_read_range` за квант, 32–64 КиБ (по умолчанию 64 КиБ), два вращающихся буфера по 64 КиБ, копия только кванта |
| Окно | запрос — префикс `[0, min(n, payload, window_max))`, по умолчанию ≤256 КиБ; malloc на всю запись отсутствует |
| Полоса | `R_cell × Δt` (по умолчанию 7 МБ/с), накопление ≤2 квантов, списание фактически прочитанных байт; при нехватке токенов pump возвращает 0 квантов и считает `budget_denied` |
| Проверка | опциональный `StreamVerifyFn`; без него `VERIFIED` означает только полное чтение окна, SHA-256 не заявляется |
| Потребление | `stream_mount_request_copy()` из READY; `stream_mount_read()` также обслуживает попадание из READY без I/O |
| Вытеснение | LRU по байтам только для READY без потребителей, не pinned и не visible; сначала отменяется невостребованный P2 в очереди; `trim()` явно освобождает до целевого объёма |
| Учёт | allocs/frees, bytes_allocated/bytes_freed, cache_bytes/peak, quanta, seeks, dedup, expired, evicted, ready, errors |

Часы инъектируются (`stream_mount_set_clock`) в наносекундах; по умолчанию
используется `clock()` как переносимый запасной вариант, устройство должно
поставить тиковый монотонный источник. `stream_mount_configure()` принимает
квант 32–64 КиБ, окно ≥ кванта, лимит кэша и скорость.

`tests/stream_queue_smoke.c` — детерминированная модель на синтетическом
`stream_index` + BSA: искусственные часы, 10 МБ/с, 64 КиБ кванты,
порядок demand/P0/P1/P2, дедуп и расширение окна, отмена, дедлайн, проверка,
LRU/pin, лимит 256 дескрипторов и баланс alloc/free. 67 проверок.

## Что осталось (TODO следующих фаз)

- **GPU-публикация.** READY — это RAM, не SKTX/fence/кадр.
- **Многопоточность.** Исполнитель синхронный (pump в вызывающем потоке);
  отдельного I/O-потока и блокировок нет.
- **Окна с произвольным `rel`.** Поддерживается только префикс ресурса;
  хвостовые окна и объединение соседних записей не реализованы.
- **Таблица клеток.** Формат зарезервирован, содержимого нет.
- **Интеграция с TESV.** `s_ReadFile()`/read-only mapping ещё не ходят через
  `asset_stream`; ускоренные диапазоны не подключены к игровому I/O.
- **Бюджет индексов.** `BsaOptions` для каждого архива берётся по умолчанию;
  нужен общий лимит и выгрузка незакреплённых индексов.
- **Установка и монтирование.** Проверка полного SHA-256 архива на устройстве
  не делается: при монтировании сверяются поколение, имя и размер; хеши
  проверяются установщиком. Нет выбора «последнего полного поколения».
- **Loose-замены.** Инвалидация SKTX/диапазонов/токенов по источнику не
  реализована.

## Расхождения с планом и измерения

- План предлагал `int bsa_read_range(...)`; используется `BsaStatus` и
  `const BsaArchive *`, как в остальном API (`bsa_read`, `bsa_read_prefix`).
- Таблица архивов берёт имя/размер/SHA-256 из `manifest["archives"]`, но
  приоритет и число файлов проверяются по фактическим строкам; таблица
  ресурсов целиком строится из `BsaFileEntry`, а не из оценок.
- В манифест cooked-сборки добавлены `files[].archive` и
  `files[].source_sha256`: без первого нельзя связать строку с частью, без
  второго — сохранить идентичность исходного победителя после конвертации.
- `com` в этом worktree не собирается из-за отсутствующего сгенерированного
  `rt_table.h` (артефакт `staged/`, не входит в коммит). К изменениям
  streaming отношения не имеет.
